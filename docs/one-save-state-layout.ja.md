# 保存・復元用状態レコードの調査

2026-09-20、ONE Disc 1 / SLPS-01972。
セーブファイル全体の仕様は未確定だが、RAM内の状態をまとめる処理と、
そこから復元する処理に対応するレイアウトを確認した。
以下は原作ゲームの内部レコードであり、エミュレーターのセーブステート形式ではない。

## 確認できた構造

構築関数0x8002A914は0x801B3110を基点として値をまとめる。
この処理は文章処理からも呼ばれるため、カードへ保存する瞬間だけの処理ではない。
0x80029B9C以降ではこの領域を128バイト単位で別バッファーの選択位置へコピーする。

| レコード内オフセット | サイズ | 内容・対応するRAM |
| --- | --- | --- |
| 0x00 | 20バイト | 数値変数、0x800FA840からコピー |
| 0x28 | 18バイト | ビットフラグ、0x800FA808からコピー |
| 0x52 | 18バイト | 0x800FA7E0からコピー、意味は未確定 |
| 0x64 | 9バイト | 0x800FA7F8からコピー、意味は未確定 |
| 0x7C | 2バイト | 先頭0x6Dバイトのバイト値合計、16ビットLE |

未記載の範囲を空き領域とは断定しない。ほかにも状態値を書き込むコードがある。
フラグ18バイトは144ビット相当。命令0x68で指定できる256番号すべてを
このレコードに保存しているわけではない。残りの番号の用途・保存先は未確認。

復元関数0x800329E0は0x80079AF8を基点に、同じ相対位置から
数値20バイト、フラグ18バイト等を対応する実行用RAMへ戻す。
構築側と復元側で、数値とフラグのサイズ・位置が対応している。

## RAMでの検証

以前取得した冒頭RAM（intro-checkpoint/ram.bin）で以下を確認した。

- 数値20バイトが実行用RAMと一致。
- フラグ18バイトが実行用RAMと一致。ただしこの時点では全ビット0。
- 先頭109バイトの合計1658と、+0x7Cの保存値1658が一致。

フラグが全0の一致だけでは、非ゼロのフラグが正常に保存・復元されることまでは
証明できない。コピー処理の静的解析と合わせた、内部レコードの検証である。

## メモリーカードまでの未確認点

バッファー0x801B3490の128バイト単位の位置と、文字列
`BISLPS-01972KISETSU`を引数に渡す呼び出しが0x80029C70にある。
この文字列はカードファイル識別名の候補。カードI/O末端とファイル内の
オフセット・スロット配置は引き続き追跡が必要。

実際のカード保存と読込を往復する検証はまだ行っていない。
セーブには進行フラグ以外にも、場面・文章位置・表示や音声の復元に必要な状態が
含まれる可能性がある。それぞれのフィールドの用途と、システムデータ等の別領域を
確認してからWindows側の保存形式へ対応付ける。

## 再現

```powershell
python tools/one-analysis/inspect_state_record.py .tools/redux-analysis/intro-checkpoint/ram.bin .tools/redux-analysis/new-state-record.json
```

出力先は未作成ファイルを指定。カードイメージではなく2 MiBのRAMを入力する。
一致しなくても、実行状態が内部スナップショットから進んだ可能性があるので、
それだけで破損とは判定しない。
